## What "MVP complete" means for this project
Per build-sequencing-roadmap.md, laundry.co.ke is first in the build order (lowest risk, simplest booking model — the proving ground for the shared platform core). Its MVP is: customer booking with slot selection, single-operator matching, M-Pesa payment, a basic e-commerce store (detergent/supplies), and review submission — built on shared modules 1–4 (identity/auth, payments core, booking engine v1, escrow & commission engine v1). Trust tier is mostly Tier 1/2 (see shared-architecture.md's trust-tiering table). Subscriptions, loyalty points, and the operator earnings dashboard are V2 — don't block DONE on them even though controllers for some already exist.

- Customer can sign up / log in
- Customer can book a pickup: address, date/time slot, garment count/type, service tier (wash & fold / dry clean / express)
- System matches the booking to the nearest available operator by service area + capacity (see `machine_capacity` in database-schema.md)
- Customer pays via M-Pesa STK Push at booking confirmation; operator is paid out via escrow after delivery confirmation, per shared-architecture.md's Escrow & Commission Engine and M-Pesa callback idempotency requirements
- Customer sees a live order status timeline (Requested → Picked Up → Washing → Ready → Out for Delivery → Delivered)
- Customer can submit a review after delivery
- Customer can buy detergent/supplies/packaging from the store (see prd.md's E-Commerce Store Scope)
- Admin/dispatcher can view all bookings and override status
- Every image slot (homepage hero, service/how-it-works imagery, store product photos for detergent/supplies) shows a real, topically relevant photo sourced from Unsplash — not a placeholder box or broken image
- App builds and runs with zero errors, works on mobile width
- Core flow (sign up → book → pay → track → review) covered by a smoke test

## Known issues / open questions
- **Review submission implemented this pass** (`ReviewController::store`/`forOperator`): the prior version trusted a client-supplied `reviewee_id` with no ownership check, no rating validation, no completed-booking check, no duplicate-review guard, and left the `operator_quality_scores.average_rating` TODO unaddressed. Rewrote it to: verify the caller is actually a party to the booking (customer or operator, row-locked `FOR UPDATE`) and derive `reviewee_id` server-side as "the other party" rather than trusting client input; require `status = 'delivered'` before a review is allowed; validate `rating` is an integer 1–5; enforce one review per (booking, reviewer) via a new `UNIQUE (booking_id, reviewer_id)` constraint added to both `schema.sql`/`schema.postgres.sql` (and applied live to the local MariaDB dev database via `ALTER TABLE`) plus an app-level pre-check returning 409; and recompute `operator_quality_scores.average_rating`/`completed_orders_count` directly from the `reviews`/`laundry_bookings` tables (not an incremental running average, so it self-corrects if rows are ever edited) whenever a customer reviews an operator, using the same MySQL/Postgres upsert-branch pattern as `OperatorController::prefer()`. Also wired a review form into `booking-status.php`'s existing 5s polling loop — it appears once `booking.status === 'delivered'`, submits to `POST /api/v1/bookings/{id}/review`, and handles the 409 (already reviewed) and 401 (logged out) cases. **Resolved open-questions.md #5 (mutual review) as: yes, mutual** — api-endpoints.md's contract already lists the review endpoint's auth as "Customer, Operator" (both sides), so both are allowed to rate each other on a delivered booking; only the customer→operator direction feeds `operator_quality_scores` (there's no customer-side trust-score field yet to feed the reverse direction into, consistent with this schema). Verified end-to-end against a live local MariaDB: customer review 201s and updates the operator's quality score (5.00 avg / 1 completed order), operator-reviews-customer 201s, duplicate review 409s, rating=9 422s, unauthenticated request 401s, non-`delivered` booking 422s, and `GET /api/v1/operators/{id}/reviews` correctly excludes operator-authored (reviewee=customer) rows.
- Commission rate and pay-on-delivery toggle are still explicitly unresolved in open-questions.md — needs stakeholder input, not an engineering blocker. Reasonable defaults already picked and logged below; continuing.
- **Booking creation + operator matching implemented this pass** (`BookingController::create`/`matchOperator`/`availableSlots`): nearest-operator-by-radius matching against `operator_service_areas` (radius type only) + `machine_capacity` (slot/weight/order-count capacity, row-locked with `FOR UPDATE` inside a transaction to avoid two concurrent bookings over-filling the same slot), excluding suspended operators via `operator_quality_scores`. Matching is synchronous at booking time (no operator accept/decline window — there's no operator app to accept from yet), consistent with MVP_STATUS's "single-operator matching" scope. Verified end-to-end against a live local MariaDB: ISO 8601 `Z`-suffix datetimes now parse correctly (fixed via `DateTimeImmutable`, closing the previously-logged datetime bug below), capacity correctly increments and caps out (tested 3/3 `max_orders` then correctly falls through to "no operator available" rather than overbooking), and `book.php` now collects `pickup_lat`/`pickup_lng` via the browser Geolocation API (closing the previously-logged missing-lat/lng bug below) with a real slot picker wired to the customer's location and passed through to booking creation.
- **Assumptions made this pass (no stakeholder input available, logging per instructions):** (1) Open question #3 (operator pricing autonomy) resolved for MVP as "platform sets a fixed per-item price card" (`BookingController::SERVICE_TIER_RATES` — wash_fold 150/dry_clean 300/express 250 KES per garment) since operators have no pricing-setting UI yet; revisit if operator-set pricing is decided. (2) When no estimated weight is given, weight is approximated as `item_count * 0.4kg` (rough household-laundry average) purely for capacity-matching purposes — the real weight is still recorded by the operator at pickup via `confirmWeight`. (3) When no operator has capacity for the requested address/slot, the booking is still created with status `requested`/`operator_id = null` (rather than rejected outright) so the customer's request isn't lost — this is the schema's documented meaning of `requested` (not yet matched) and is surfaced to the customer with a clear message.
- **Named-neighborhood service areas aren't matchable yet.** `matchOperator()`/`availableSlots()` only query `operator_service_areas` where `area_type = 'radius'` — `named_neighborhoods` areas need address→neighborhood resolution (a geocoding step) that isn't built, and no geocoding provider is wired into this project. If an operator is onboarded with a `named_neighborhoods` service area, they will never be matched. Low risk for MVP since `OperatorController::setServiceArea` still accepts either type without validation against what's actually usable — worth either restricting the onboarding UI to radius-only for now, or building the neighborhood-resolution step, in a future pass.
- `OperatorController::getCapacity` used MySQL-only `CURDATE()`; switched to the portable `CURRENT_DATE` (supported by both MySQL/MariaDB and Postgres) since this repo now runs against both (see `Database::driver()`).
- ~~`Database::driver()` was a stub always returning 'mysql'~~ — since resolved (by a concurrent session, per the note logged in this file's prior pass): `src/Config/Database.php` now properly branches on `getenv('PGHOST')` between a MySQL DSN (local dev) and a Postgres DSN (Vercel/Neon Marketplace), so `Database::driver()` correctly reflects which is active. Verified this pass by reading the current file — no action needed.
- ~~Booking creation didn't accept ISO 8601 `Z`-suffix datetimes~~ — fixed in a prior pass.
- ~~`pickup_lat`/`pickup_lng` weren't collected in the booking form UI~~ — fixed in a prior pass via the Geolocation API.
- **M-Pesa payment + escrow implemented this pass** (`src/Core/Mpesa.php`, `src/Core/Escrow.php`, `PaymentController::stkPush`/`mpesaCallback`, `BookingController::confirmReceipt`): real Daraja OAuth + STK Push client (not a stub) using `MPESA_*` env vars; a `payments` row is created with the returned `CheckoutRequestID` as `external_reference`. `mpesaCallback` is idempotent per shared-architecture.md — every inbound callback is first inserted into `payment_callbacks_log` keyed by `CheckoutRequestID` (`UNIQUE`), and a duplicate delivery hits the unique-constraint and is acked as a no-op rather than reprocessed (verified: resending an identical callback did not create a second escrow row). On a successful callback, `Escrow::hold()` opens an `escrow_transactions` row sized by shared-architecture.md's trust-tiering table (Tier 1 <5,000 KES: 0% retention, release on customer confirmation; Tier 2 5,000–100,000: same, plus a `release_at` +48h timestamp recorded for a future auto-release job; Tier 3 ≥100,000: 10% retention, `admin_release`). `BookingController::confirmReceipt` now checks booking ownership (403 if the requester isn't the booking's customer), is idempotent (re-confirming an already-delivered booking is a no-op, doesn't double-pay), and calls `Escrow::release()`, which computes commission from a `commission_rules` row (seeded at 18%, falls back to the same 18% in code if the row is ever missing), inserts a `commission` ledger row (settled immediately, same rail as the original charge) and a `payout` row (`status='pending'`, `method='mpesa_b2c'`, picked up by `PaymentController::myEarnings`). **Verified end-to-end against a live local MariaDB**: STK Push correctly reaches Daraja's sandbox OAuth endpoint and fails cleanly (503/502, not a fatal error) when unconfigured or unreachable; a simulated successful callback moved a payment to `completed` and opened a Tier-1 escrow hold; a duplicate callback was a true no-op (escrow/log row counts stayed at 1); `confirmReceipt` released escrow into an 18%-commission/82%-payout split (1,000 KES → 180 commission / 820 payout) and was rejected with 403 when attempted by a non-owning customer; re-confirming returned `already_settled` without creating duplicate payout rows. `card()` now returns a real `501` instead of a fake `202 card_charge_initiated` — the card gateway isn't wired and card payments aren't part of this platform's MVP cut (shared-architecture.md notes the card rail matters more for construction.co.ke/solar.co.ke's higher transaction values). Added a "Pay with M-Pesa" phone-entry form and a "Confirm delivery received" button to `booking-status.php`, wired into its existing 5s polling loop.
- **Local Windows dev environment has no CA bundle configured for PHP's curl** (`curl.cainfo`/`openssl.cafile` both empty) — every outbound HTTPS `curl_exec` in this environment fails with "SSL certificate problem: unable to get local issuer certificate", confirmed against both Safaricom's sandbox host and `api.github.com`, so it's an environment-wide gap, not an application bug. This blocks live end-to-end testing of `Mpesa::stkPush()` against Daraja's real sandbox in this environment (verified instead by injecting fake credentials and confirming the request is correctly built and reaches the network before failing on the cert check, then testing the rest of the payment/escrow pipeline by simulating a Daraja callback directly). Vercel's Linux runtime ships a proper CA bundle, so this should not reproduce in production — but if a future pass sees the same error there, install a CA bundle (`curl.cainfo` pointing at a `cacert.pem`) rather than disabling SSL verification, which would be a real vulnerability for a payment integration.
- **Real Daraja sandbox credentials still aren't available** (`MPESA_*` are blank in `.env`/`.env.example`, per instructions not to block on stakeholder input) — `stkPush`/`mpesaCallback` are implemented against Daraja's documented contract and verified as described above, but a live STK Push round-trip against Safaricom's actual sandbox has not been run. Do this once credentials are provisioned.
- **B2C payout disbursement isn't built.** `Escrow::release()` correctly computes the commission/payout split and records a `payments` row with `type='payout', status='pending'`, but nothing calls Daraja's B2C API to actually move KES to the operator's M-Pesa account — that requires a separate payout-batch job plus B2C-specific credentials (initiator name, security credential) not yet in scope. This matches open-questions.md's payout-frequency question (assumed daily batch) — build the batch job in a future pass.
- **Assumptions made this pass:** (1) Commission rate set to 18% (midpoint of prd.md's proposed 15–20% range), seeded as a `commission_rules` row in both `schema.sql`/`schema.postgres.sql` and duplicated as a code fallback in `Escrow::commissionRate()`. (2) `pay_on_delivery` bookings skip the escrow flow entirely (no STK Push prompt, no escrow hold) — `confirmReceipt` just marks the booking delivered, on the assumption the operator collects payment directly at drop-off; open-questions.md #2 (pay-on-delivery eligibility) is still unresolved by the business, so this may need revisiting. (3) Trust-tier thresholds for escrow retention/release-condition are read directly off shared-architecture.md's KES bands (5,000 / 100,000) applied to a single booking's amount, since laundry.co.ke has no separate customer-level trust-tier field yet.
